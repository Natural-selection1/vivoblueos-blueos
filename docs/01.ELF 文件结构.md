# 01. ELF 文件结构

本文面向刚开始接触可执行文件加载的开发者。
目标是：拿到一个 ELF 文件，能说明 loader 应该读取什么，以及为什么。

本系列以刘闯提供的[最高设计](loader流程说明.md)为准，以 `98a6f0cf` 为实现基线。
先读[任务导航](README.md)，区分设计要求、已有代码和建议方案。文中的地址均为教学示例。

## ELF 是带有结构信息的二进制文件

ELF（Executable and Linkable Format）用于描述目标文件、可执行程序和共享对象。
它包含机器指令、数据以及解释这些内容所需的元数据。

可以把 ELF 类比为一种序列化格式：文件头说明格式版本和索引位置，索引描述各块数据。
它不是把一个 Rust 结构体的内存原样保存到磁盘。读取时必须处理字节序、整数宽度、字段布局和边界检查。

loader 的输入可以是 `&[u8]`，也可以是支持按偏移读取的文件接口。
文件来自磁盘、内嵌数组还是测试环境的宿主文件，不改变 ELF 的核心加载规则。

## 三种头分别回答什么问题

- 结构：ELF Header
  主要问题：这是什么格式、架构、文件类型？入口和其他表在哪里？
  对进程 loader 的意义：首先读取并验证

- 结构：Program Header Table
  主要问题：哪些文件内容需要放进运行时内存？有什么属性？
  对进程 loader 的意义：装载程序的主要依据

- 结构：Section Header Table
  主要问题：编译链接产生了哪些代码、数据、符号和调试区块？
  对进程 loader 的意义：分析文件有用，通常不是装载依据

ELF Header 常见字段：

- `e_ident`：包括 magic、32/64 位类别和字节序。magic 是 `7f 45 4c 46`。
- `e_type`：文件类型，例如 `ET_REL`、`ET_EXEC`、`ET_DYN`。
- `e_machine`：目标指令集，例如 AArch64 或 RISC-V。
- `e_entry`：入口的 ELF 虚拟地址，不是文件偏移，也不必叫 `main`。
- `e_phoff/e_phentsize/e_phnum`：
  Program Header 表的文件偏移、单项大小、项数。
- `e_shoff/e_shentsize/e_shnum`：Section Header 表的对应信息。

magic 正确只说明文件像 ELF，不能证明它是当前机器可执行的有效程序。

## Section 和 segment 为什么不是一回事

section 是编译、链接视角的组织单位。例如：

- `.text`：机器指令。
- `.rodata`：只读数据。
- `.data`：有初值的可写数据。
- `.bss`：运行前应为零的数据，通常不为这些零逐字节占用文件空间。
- `.symtab`、`.debug_*`：符号和调试信息。

segment 是运行时装载视角的区域，由 Program Header 描述。
一个 segment 可以覆盖多个 section。
链接器可能把 `.text` 和 `.rodata` 放在同一个可加载段，也可能分开。

```text
链接时组织                     运行时装载
.text ─────┐
.rodata ───┴──────────────→ 一个 PT_LOAD（示意：R-X）
.data ─────┐
.bss ──────┴──────────────→ 一个 PT_LOAD（示意：RW-）
.debug_info ─────────────→ 通常不映射到进程内存
```

因此，loader 不应依靠名字查找 `.text`、`.data`、`.bss` 再分别复制。
合法可执行文件可以不带可用的 Section Header Table；
只要装载所需的 Program Header 和数据有效，仍可能运行。

## Program Header 中会遇到什么

- 类型：`PT_LOAD`
  含义：需要装入进程地址空间的段
  首期处理方式：核心支持对象

- 类型：`PT_INTERP`
  含义：指定用户态解释器，通常是动态链接器的路径
  本次职责：读取路径、加载解释器，并将首次执行入口设为解释器入口；阶段性未实现时明确报错

- 类型：`PT_DYNAMIC`
  含义：动态链接相关信息，如重定位表地址
  本次职责：相关内容随 PT_LOAD 装入；依赖解析和重定位交给用户态，不能因存在此项就启动内核动态链接

- 类型：`PT_PHDR`
  含义：描述 Program Header 表在内存中的位置
  首期处理方式：构造 `AT_PHDR` 时有帮助；该项可以不存在

- 类型：`PT_TLS`
  含义：线程局部存储模板
  首期处理方式：需要与运行时约定；首期可限制使用

- 类型：`PT_GNU_STACK`
  含义：GNU 扩展，声明栈相关属性
  首期处理方式：按支持策略解释，不是要复制的普通段

不能把所有 Program Header 都当成待复制区域，也不能把所有不认识的项一律当成错误。
要区分可以忽略的元数据与当前不支持、但运行程序必需的功能。

## 一个贯穿后续章节的例子

假设某个 `PT_LOAD` 如下，数值均为十六进制：

```text
p_offset = 0x1000    文件内容从这里开始
p_filesz = 0x0600    文件提供的字节数
p_vaddr  = 0x2000    ELF 所描述的虚拟地址
p_memsz  = 0x0a00    运行时需要的字节数
p_align  = 0x1000    段对齐约束
```

它要求从文件读取 `[0x1000, 0x1600)`，放到该段的运行时地址，接着补上 `0x400` 个零。
真正运行时地址还取决于是否给 ELF 加上装载偏移量，见第 02、05 篇。

这里所有区间使用 Rust 常见的左闭右开表示法 `[start, end)`，长度为 `end - start`。

## 对照 `98a6f0cf`

[prepare_image][ref-1] 是阅读入口，但其完整流水线包含重定位，不能直接当作目标设计。
格式校验在 [image_loader.rs](../kernel/loader/src/image/image_loader.rs)，
Program Header 检查在 [admit.rs](../kernel/loader/src/image/admit.rs)，
布局规划在 [inspect.rs](../kernel/loader/src/image/inspect.rs)。
它们通过 `ElfReader` 按偏移读取并解码字段；不要再按旧版 `Elf::parse → build_memory_layout` 的函数名找代码。

已有可信 `LoadProfile`、范围检查和资源限制可复用。
但当前 `LoadPolicy` 拒绝 `PT_INTERP`，并按内核链接器能力检查动态特性。
新加载路径必须将“内核映射需要的检查”与“用户动态链接器需要的检查”分开，详见第 11 篇。

## 如何确认自己掌握了

对一个测试 ELF 执行 `readelf -hW` 和 `readelf -lW`，应能回答：

1. 它面向哪个架构，是 `EXEC` 还是 `DYN`？
2. 有几个 `PT_LOAD`，每个段读取多少文件字节、占多少运行时内存？
3. 有没有 `PT_INTERP`？
4. 为什么去掉调试 section 不一定影响加载？

能回答这些问题，就可以继续学习地址模型，无须先掌握 ELF 的全部 section 类型。
