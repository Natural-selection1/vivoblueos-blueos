# 02. 地址的不同含义

loader 中最容易出错的是：几个变量都是 `usize`，却分别代表完全不同的坐标。
目标是看到一个地址时，能立即说出它属于哪个文件或地址空间。

## 先分清五种坐标

| 名称         | 含义                                    | 能不能直接作为内核指针使用             |
| ------------ | --------------------------------------- | -------------------------------------- |
| 文件偏移     | 距 ELF 文件开头多少字节                 | 不能；先用于文件读取或输入切片索引     |
| ELF 虚拟地址 | 链接器写进 ELF 的地址坐标，如 `p_vaddr` | 不能自动假设可以                       |
| 用户虚拟地址 | 程序在自己的地址空间中使用的地址        | 不能自动假设当前内核可访问             |
| 内核访问地址 | 内核当前可以用来读写这块内存的虚拟地址  | 映射、范围和 Rust 安全条件均满足时可以 |
| 物理地址     | 页表等机制最终指向的物理内存位置        | MMU 开启后通常不能直接当普通指针解引用 |

ELF 虚拟地址和用户虚拟地址是同一条装载计算链中的两个阶段。
固定地址可执行文件通常让二者相同；
PIE 则通常增加一个统一的偏移量。

## 用一组数字建立对应关系

沿用第 01 篇的段：`p_offset = 0x1000`、`p_vaddr = 0x2000`。

假设 loader 选择装载偏移量 `B = 0x400000`，将该段映射到用户地址 `0x402000`。
内存模块为它分配一个物理页，并提供一个内核可写映射。
下表仅表示同一个字节的不同坐标，不表示本项目固定使用这些地址。

| 坐标                                  | 段内偏移 `0x20` 的字节         |
| ------------------------------------- | ------------------------------ |
| ELF 文件偏移                          | `0x1000 + 0x20 = 0x1020`       |
| ELF 虚拟地址                          | `0x2000 + 0x20 = 0x2020`       |
| 用户虚拟地址                          | `0x400000 + 0x2020 = 0x402020` |
| 物理地址（假设该页位于 `0x90000000`） | `0x90000020`                   |
| 内核访问地址（假设该页映射到 `K`）    | `K + 0x20`                     |

loader 从输入文件的 `0x1020` 读取字节，通过内核映射 `K + 0x20` 写入；
进程之后通过 `0x402020` 访问同一字节。

这个物理地址公式仅针对示例中的同一页。
跨页以后，下一个虚拟页完全可能对应不连续的物理页，不能继续盲目相加。

## load bias 是地址变换中的统一偏移

对采用这种装载模型的 ELF：

```text
运行时段地址 = B + p_vaddr
运行时入口   = B + e_entry
```

例如 `e_entry = 0x2180`，则运行时入口是 `0x402180`。

`B` 叫 load bias。它不一定等于最低映射地址。若最低段的 `p_vaddr = 0x2000`，
最低映射地址为 `0x402000`，那么：

```text
B = 0x402000 - 0x2000 = 0x400000
```

实际实现通常以对齐后的最低段地址计算，
且必须处理地址宽度、溢出和对齐要求。这里先理解坐标关系。

## 为什么拿到一个用户地址还不能写它

页表可以理解为地址翻译规则：
进程虚拟页映射到哪些物理页，以及允许如何访问。

两个进程可以都有虚拟地址 `0x402000`，却分别映射到不同物理页。
因此，单独一个数字无法唯一描述某个进程的内存；
通常还需要“属于哪个地址空间”。

loader 写入新进程时，新进程的页表未必已经启用。
即使启用了，内核访问用户页也可能受体系结构访问控制影响。
常见设计包括：

- 内存模块提供物理页的内核映射，loader 通过该映射写入。
- 提供 `write_user_memory(address_space, user_addr, bytes)`
  一类操作，由内存模块处理映射。
- 在受控环境下临时切换映射，并承担切换、异常和并发约束。

具体方案由内存模块约定。不要在 loader 里把用户地址直接强转为 `*mut u8`，
期待 Rust 或 MMU 自动完成坐标转换。

## `__pa` / `__va` 也不是通用公式

某些内核把一段物理内存连续映射到固定内核地址区，此时转换可能只是加减常量。
这叫直接映射的一种实现。

这个公式只适用于该映射区域。它不能一般性地用来转换任意用户地址、设备地址或临时映射。
相同地，ELF 的 `p_paddr` 也不能在通用用户进程 loader 中直接当作分配物理内存的指令；
固件、裸机镜像可能另有专门约定。

## 在 Rust 接口中保留这些区别

下面是概念性类型示例，不是仓库已有接口：

```rust
struct FileOffset(u64);
struct ElfVaddr(u64);
struct UserVaddr(u64);
struct PhysAddr(u64);
```

这些 newtype 不能自行保证映射存在，但可以让“把文件偏移传给用户地址参数”变成类型错误。
内核可访问的内存更适合通过带生命周期的受控访问接口表达，而不只是再定义一个数字包装。

目标 ELF 的地址宽度也不必等于执行解析器的宿主 `usize` 宽度。
先在文件格式对应的整数类型中验证，再进行有检查的转换。

## 对照 `98a6f0cf`

当前 [address.rs](../kernel/loader/src/address.rs) 已有 `FileRange`、`TargetAddress`、`TargetRange`，
[memory.rs](../kernel/loader/src/memory.rs) 已有 `AllocationOffset` 和 `ImageAllocation`。
不过 `TargetAddress` 本身仍不区分 ELF 地址与具体进程的用户地址，调用处必须保留语义。

[plan.rs](../kernel/loader/src/image/plan.rs) 按分配基址减去对齐后的最低 ELF 地址计算 bias；
`ET_EXEC` 请求固定地址，`ET_DYN` 请求可移动放置。
这部分不应重新发明，但需要验证新后端的 `base` 确实表示用户虚拟地址。

当前 application 的 [FlatImageMemory][ref-1] 用内核堆分配地址作为运行时地址，
因此旧路径中用户坐标与内核访问坐标没有真正分开。
新后端应让 `ImageAllocation.base` 表示目标用户地址，写入操作通过内核映射完成。

特别检查 `ImageMemory::image_span`：它要求返回覆盖指定范围的宿主指针。
如果未来页面物理不连续，需要提供连续的内核虚拟映射，或改造该接口以支持分段访问。
物理连续不是用户映像连续的必要条件。

测试后端应故意让用户基址与存储指针不同，避免地址混用在平坦模型里被掩盖。

## 如何确认自己掌握了

给定 `p_offset = 0x1000`、`p_vaddr = 0x2000`、`B = 0x400000`，
文件中 `0x1120` 对应的用户地址是 `0x402120`。
但仅凭这几个量，还算不出它的物理地址或内核访问地址。

如果你能解释为什么最后两个地址算不出来，就已经抓住这一组概念的重点。
