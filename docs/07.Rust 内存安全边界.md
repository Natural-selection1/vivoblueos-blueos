# 07. Rust 内存安全边界

你的 safe Rust 经验在 loader 中仍然有用：
解析、布局规划、范围检查和错误处理大多可以保持 safe。
真正需要格外关注的是，
如何把这些经过检查的信息交给操作实际内存的少量底层代码。

`unsafe` 表示程序员承担编译器无法验证的前提，
不会改变 CPU 行为，也不会使无效地址变得可访问。

## 三种正确性要分别检查

| 层次          | 典型问题                                                               |
| ------------- | ---------------------------------------------------------------------- |
| ELF 语义      | 这个文件区间存在吗？入口是否在受支持的可执行段中？                     |
| 硬件访问      | 页已映射吗？当前特权级能写吗？指令缓存已同步吗？                       |
| Rust 内存模型 | 指针有效且满足 provenance 吗？对齐、初始化、生命周期和别名规则满足吗？ |

硬件没有触发异常，不代表 Rust 操作符合语言规则。
反过来，一个 Rust 层面没有越界的字节复制，
也不代表目标页具有正确的用户权限。

## 从整数到指针，中间缺少什么证明

`address as *mut u8` 不会分配内存、建立映射、延长资源生命周期或获得独占访问权。

如果内存来自 Rust 分配器，应尽量保留原始指针，
通过受检查的偏移访问同一分配，而不是反复转成整数再重建指针。
固定映射等内核场景确实可能以地址值为起点，
但需要由底层抽象明确证明映射、有效范围和访问规则。

provenance 可以先理解为“指针从哪里来，以及它被允许访问哪块存储”。
掌握实际使用的指针 API 比简单地认为“数值相同就完全等价”更可靠。

## 裸指针操作各自要求什么

### `ptr.add(offset)`

调用者必须保证偏移符合该指针的分配边界等要求；
它不是可用于任意物理地址空间的无条件整数加法。

### `copy` 与 `copy_nonoverlapping`

两者都要求源和目标对相应长度有效。
`copy` 允许源目标重叠，`copy_nonoverlapping` 不允许。

使用允许重叠的版本只解决重叠这一项，
不会解决目标未映射、范围越界或生命周期结束的问题。
复制长度为零时，也不能任意忽略所用底层 API 的对齐和有效性要求；
更简单的设计通常在上层提前处理空操作。

### `ptr.write(value)` 与 `write_unaligned(value)`

普通 typed write 要求目标按 `T` 对齐；`write_unaligned` 放宽对齐要求，
但仍要求目标范围有效。

本次 loader 的用户栈整数和指针序列化要服从目标字长和字节序。用户态链接器的重定位写入也有同类要求。
对于只负责序列化的逻辑，先生成规定宽度的字节数组，再交给写入接口，
通常更容易审查。

### `from_raw_parts` / `from_raw_parts_mut`

创建切片就引入了引用的语义：
非 null 指针要求、有效范围、单个分配内的连续性、生命周期，
以及可变引用的独占访问约束等。

对 `&[u8]` 而言，字节还必须已初始化。
不能因为 `u8` 接受所有位模式，
就把分配器返回的未初始化内存直接当成可读字节切片。
它“尚未有值”与“某个未知但有效的数值”不是一回事。

## 对齐与 `repr(C)` 能解决什么

`repr(C)` 规定一种与 C 兼容的结构布局规则，
但不完成字节序转换，也不证明输入缓冲区按该结构对齐或已经足够长。

直接把 `&[u8]` 强转为 ELF Header 引用，需要承担多项额外前提。
使用解析库按字段读取，或者用 `from_le_bytes` 等显式转换，通常更适合读取外部格式。

对于可能包含无效位模式的类型，
例如引用、枚举和 `bool`，不能把任意文件字节直接解释成该类型。
loader 的文件格式解析与 Rust 内部数据结构应保持清楚的转换边界。

## 内存所有权要持续到程序用完

设 loader 分配代码页、计算出入口，然后返回一个 `usize`。
如果保存这些页面的所有者随 loader 局部变量一起析构，
入口数字依旧存在，底下的存储却已释放。

正确的所有权关系应保证：

```text
加载阶段持有新映像资源
    ↓ 成功交接所有权
进程持有映像及地址空间资源
    ↓ 进程停止使用，撤销映射并完成必要同步
最终释放资源
```

失败时，由尚未交接的加载上下文负责释放。
存在共享页时，还需要对应的共享所有权管理。
仅仅返回入口和 SP 两个整数，无法表达这些生命周期。

这里描述的是资源设计要求，
不是要求你在 loader 内自行实现整套进程内存管理。

## 别名、并发与权限的关系

同一个物理页可能有内核映射和用户映射。只要用户进程可以同时写入，
就不能简单地让内核长期持有一个假设没有其他写入者的 Rust 引用。

加载尚未运行的新进程时，通常更容易控制独占访问；
一旦进程开始运行，跨地址空间拷贝接口就要考虑并发、异常和生命周期。

`read_volatile` / `write_volatile` 也不能修复一般的数据竞争和别名违规。
volatile 主要约束编译器对访问的优化，不代替锁、原子或明确的所有权协议。

## 如何把 safe 和 unsafe 分开

建议按职责划分：

1. safe 解析层把外部字节变成经过校验的字段。
2. safe 规划层计算段区间、页需求、解释器布局和用户栈布局。
3. 受控内存接口负责写入与映射，并封装底层 `unsafe`。
4. process/架构层完成启动和执行期间的资源管理。

一个安全的 `write_bytes` 接口必须拒绝其承诺范围外的请求，
不能把“调用者大概知道自己在干什么”作为隐藏前提。
确实需要由调用者保证的内存安全条件，
应体现在 unsafe API 的契约中。

## 对照 `98a6f0cf`

优先阅读 [memory.rs][ref-1] 的 `AllocationLease`、`ImageLoadTransaction` 和 `ImageCommitMemory`：
未提交的事务析构时调用后端回滚；成功提交时转移唯一 lease。
`prepare_install` 先完成可能失败的准备，`commit_install` 再执行所有权交接。
这些机制可以复用，不能改成只返回两个地址后随手释放后端。

新的进程加载包含主程序、解释器和栈。单映像的事务正确，
不代表三者已经有统一的失败回收边界；需要一个共同持有者管理提交前的资源。
内存后端和进程之间还要约定谁拥有物理页、谁拥有映射，避免两方重复释放。

阅读 [Storage][ref-2] 和 application 的 `FlatImageMemory` 时，
关注原始指针、初始化和释放之间的联系，但不要把平坦内存的访问假设照搬到用户空间。

Miri 可帮助验证能在其环境中执行的解析、缓冲区和所有权逻辑；
不能代替真实 MMU、异常返回和指令缓存行为的目标平台验证。

## 如何确认自己掌握了

看到一个 `unsafe` 块，你应能具体回答：
地址对应什么资源，谁保证范围和对齐，内存何时初始化，有没有其他访问者，
资源何时释放。回答不能只是“前面已经检查过”，
而应能指出哪个接口维护了哪一项不变量。
