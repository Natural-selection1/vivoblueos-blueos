# 04. 分页与权限

ELF 按 segment 描述程序，MMU 按 page（页）翻译和保护内存。
loader 需要把前者的要求转换为后者能执行的映射请求。

你需要理解映射接口的语义；
多级页表的具体格式、页表页的分配和底层寄存器操作，可以由内存与架构模块封装。

## 页是地址翻译和保护的基本单位

以 4 KiB 页为例，一个页有 `4096 = 0x1000` 字节。
虚拟地址可以拆成“虚拟页编号 + 页内偏移”。

```text
用户虚拟地址 0x402120
             ↓
虚拟页起点   0x402000，页内偏移 0x120
             ↓ 页表翻译
物理页起点   0x90000000
             ↓ 保留页内偏移
物理地址     0x90000120
```

页表项同时记录有效性、访问权限等属性。
多级页表是节省页表空间的索引结构；loader 通常不需要直接遍历每一级。

4 KiB 是本文的教学假设。
真正的页大小或翻译粒度由目标平台和内存模块决定，不应在通用 loader 中随意写死。

## 将字节区间扩展成页区间

设页大小为 `P`，且为二的幂。对于非空区间 `[start, end)`：

```text
page_start = align_down(start, P)
page_end   = align_up(end, P)
```

例如 `[0x402080, 0x403180)` 覆盖两页，页区间为 `[0x402000, 0x404000)`。

`align_up` 通常包含加法，因此也会溢出。
不能把对齐运算看作天然安全的位运算。
空区间应单独处理，避免凭空多分配一页。

还要区分：

- 段的有效字节区间：程序真正声明使用的内容。
- 页映射区间：为了覆盖这些内容而必须映射的整页。

页内填充不自动成为 ELF 合法入口或合法重定位目标。

## `p_align` 与页大小分别约束什么

`p_align` 是 ELF 中的段对齐要求。
取值为 0 或 1 时表示没有额外对齐要求；
其他有效值应为二的幂，并满足 `p_vaddr` 与 `p_offset` 对该值同余。

在通常的分页装载中，还需要满足目标平台相应的文件偏移与虚拟地址页内偏移约束。
load bias 的选择也必须维持 ELF 要求的运行时对齐。
`p_align` 大于页大小时，只做到按页对齐可能还不够。

若首期只支持某个链接器生成的布局，
应把支持条件写清楚，并对不满足的文件返回错误。

## R/W/X 是请求，页表才执行限制

ELF 的 `p_flags` 包含：

- `PF_R`：需要读取。
- `PF_W`：需要写入。
- `PF_X`：需要执行。

常见映射为代码 RX、只读数据 R、可写数据 RW。
用户页还需要用户态访问许可；仅有读写执行三位并不足以描述特权隔离。

底层硬件的编码与 ELF 标志不一定一一对应。
例如 RISC-V 的某些 R/W 组合是无效页表编码，
AArch64 则通过访问权限和执行禁止等字段表达要求。
内存模块应负责把抽象权限转换为合法硬件配置，
并对不能支持的组合制定策略。

一个 Rust `MemoryPermissions` 值本身不会阻止 CPU 写入或执行。
只有权限被落实到有效映射或其他硬件保护机制，才具有运行时约束力。

## 两个段共享一页时怎么办

假设代码字节到 `0x402800` 结束，数据从 `0x402800` 开始，
而页范围是 `[0x402000, 0x403000)`。代码要求 RX，数据要求 RW，
硬件却只能给整个页设置同一组权限。

这与两个段字节重叠不同：字节区间可以不重叠，但权限仍发生页级冲突。

常见策略是让链接器把权限不同的段放到不同页；
loader 首期可以要求这种布局并拒绝冲突。
直接将权限求并集会得到 RWX，
可能违反 W^X（可写与可执行不同时开放）的策略，不能不经约定就这样处理。

## 加载时写入与运行时只读并不矛盾

loader 需要往代码页写机器指令，但用户运行时通常只应读取和执行它。
可以通过受控内核写映射初始化物理页，再给用户建立最终 RX 映射；
也可以在不可运行的新地址空间里暂时写入，再收紧权限。

关键是规定何时允许写入、何时允许执行，以及是否还留着长期可写的别名。
具体机制由内存和架构模块实现。

这里还涉及两种不同的一致性问题：

- 页表或权限改变后，TLB 中缓存的地址翻译是否需要失效？
- 复制新机器码后，指令获取是否能看到最新内容？
- AArch64 可能需要数据/指令缓存维护，
  RISC-V 涉及适用的指令同步操作，例如 `FENCE.I`。

它们不是同一件事。多核场景还需要考虑其他核。
loader 应调用约定好的“完成映像准备”接口，
而不是把一段孤立汇编当作所有平台通用方案。

## 缺页和立即装载

立即装载会在进入程序前准备所有必要页面，最适合首个可运行版本。

按需分页则先登记虚拟区域，在程序访问尚未准备的页时，
通过缺页异常补齐内容。
此时 loader 与缺页处理器需要共享文件内容和零填充规则，
文件对象也要保持有效，复杂度更高。

这两种方式都是对程序映像的实现策略。
首期不必为了将来支持缺页而先实现全部机制，
但接口不要把用户虚拟地址与连续物理内存绑定死。

## RELRO 的保护时机要随职责改变

`PT_GNU_RELRO` 描述重定位完成后应收紧为只读的区域。
它可能位于一个原本可写的 `PT_LOAD` 内，重定位期间仍需修改其中的地址槽。

现有 [SealPlan::build](../kernel/loader/src/image/seal.rs) 会移除 RELRO 范围的写权限，
因为旧路径在此之前已经在内核完成了重定位。
目标设计改为用户态重定位后，不能直接照搬这个 `seal` 阶段。
内核先落实段装载权限；用户态链接器完成重定位后，再通过约定的内存保护接口收紧 RELRO。

不能为了避免这个问题把所有段永久映射为 RWX。
首期可以明确限制需要修改只读代码的程序，但应将这种限制与普通的可写数据重定位区分。

## 对照 `98a6f0cf` 与掌握标准

[FlatImageMemory][ref-1] 的 `protect` 返回 `ProtectionLevel::LogicalOnly`，
没有据此建立用户页表权限。通用 crate 的 `ImageProtectionMemory` 已提供保护接口，
其粒度、别名校验和权限记录可参考，但仍需接入真实地址空间。

[ArchitectureCodeCache](../kernel/loader/src/cache.rs) 已包含架构同步逻辑。
新后端必须确认缓存操作使用的地址在当前上下文有效，并明确跨核执行时的同步责任。
已有汇编不能自动解决用户地址与内核别名不同的问题。

你应能与许昌确认：页大小、分配/映射/写入接口、用户访问许可、清零责任、
缓存与 TLB 维护责任，以及失败时如何撤销映射。
