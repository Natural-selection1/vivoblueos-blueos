# 05. PIE 与重定位

PIE（Position Independent Executable，位置无关可执行文件）允许程序在不同装载位置运行。
它不保证“复制完段就能直接执行”：代码、数据中的地址、启动代码和动态链接器必须共同满足运行约定。

本次应掌握的是如何识别程序的重定位需求，以及谁负责满足它。
按照[最高设计](loader流程说明.md)，内核 loader 不执行符号解析、重定位和 GOT/PLT 填充。
这也包括看似简单的 `RELATIVE` 重定位。

## 文件类型、PIC 与链接方式分别说明什么

| 概念 | 含义 | 不能据此推断什么 |
| --- | --- | --- |
| `ET_EXEC` | 通常按固定虚拟地址链接的可执行文件 | 不代表一定静态链接 |
| `ET_DYN` | 可重定位装载的共享对象类型，PIE 通常使用它 | 不代表一定有解释器，也不代表没有重定位 |
| PIC | 位置无关代码生成方式 | 单独开启不能保证整个 ELF 可直接运行 |
| 静态链接 | 所需库实现通常在链接时纳入产物 | 静态 PIE 仍可能需要运行时自重定位 |
| 动态链接 | 部分依赖和地址绑定留到运行时 | 在本次设计中由用户态完成 |

应分别检查 `PT_INTERP`、`DT_NEEDED` 和重定位表，不能用其中一个代替另外两个。
尤其不能将“没有 PT_INTERP”简单理解为“没有重定位，也不需要运行时支持”。

## load bias 用于整个映像

假设最低段的 ELF 地址为 `0x2000`，实际映射到 `0x402000`：

```text
B = 0x402000 - 0x2000 = 0x400000
入口 = B + e_entry
每个段的用户地址 = B + p_vaddr
```

同一个映像的所有段使用同一个 bias，保持相对位置。
主程序和解释器各自有独立的 bias，但都位于同一个新进程地址空间。
物理页可以不连续，不能给同一映像的各段随意安排互不相关的用户地址。

## 为什么 PIC 仍可能需要重定位

代码可以通过 PC 相对指令找到一个数据槽，但槽中保存的绝对指针仍依赖实际装载地址。
重定位表记录“在哪里写、写什么、采用什么规则”。并非每项都需要查符号。

以这里讨论的指针宽度 RELATIVE 重定位为例：

```text
目标槽用户地址 P = B + r_offset
槽内应写入的值 V = B + A
```

例如 `B = 0x400000`、`r_offset = 0x2300`、`A = 0x2450`，
则用户态重定位代码应在 `0x402300` 写入指针值 `0x402450`。
`P` 与 `V` 含义不同，不能把其中一个当作另一个。

`REL` 通常从目标位置取得 addend；`RELA` 在记录中显式保存 addend。
还有 RELR 等编码。执行重定位的一方负责类型支持、范围、字长、字节序和溢出检查。
这些知识用于理解产物和联调，不意味着要在本次内核 loader 中实现它们。

## 本次支持的两条启动路径

### 带解释器的程序

```text
内核：映射主程序 → 映射 PT_INTERP 指定的解释器 → 建用户栈
用户态：解释器启动/必要的自重定位 → 加载依赖 → 重定位 → 交给主程序
```

解释器本身也必须能够在尚未由别的链接器修补时开始执行。
把旧 `DynamicLinker` 编译成一个共享库，并不会自动得到这样的启动能力。

### 不带解释器的程序

内核映射后直接进入主程序入口。因此，主程序必须不需要运行时重定位，
或者具有能在用户态自行完成重定位的启动代码。

建议第一个受控 PIE 样例不依赖共享库、不需要运行时重定位，直接读取初始栈并报告结果。
这能先验证映射与用户态启动。它是阶段性测试，不代表完整动态链接已实现。

若样例确实有重定位，不应临时加回内核重定位来掩盖缺少启动运行时的问题。
对约定的样例支持范围应在构建检查和测试说明中明确。

## GOT / PLT 学到什么程度即可

GOT 存放运行时地址，PLT 常用于间接调用外部函数。
对你当前的内核 loader 工作，能从 ELF 中识别相关依赖并知道由用户态修补即可。
完整符号搜索、版本匹配、延迟绑定、`dlopen` 和构造函数排序，不是当前内核加载路径的待办。

TLS、构造函数和运行时初始化在用户态各组件间的具体分工仍需遵守选定运行时，
但不能继续由内核为应用解析并传入构造/析构函数计划。

## 对照 `98a6f0cf`

[prepare_image](../kernel/loader/src/lib.rs) 包含单映像重定位步骤；
[dynamic_linker](../kernel/loader/src/dynamic_linker/) 进一步实现了依赖闭包、符号作用域、重定位与发布。
[relocation](../kernel/loader/src/relocation/) 已有 ARM、AArch64、RISC-V 的实现。
旧文档“只处理 R_RISCV_RELATIVE，其他类型跳过”的描述已过时。

这些代码可作为理解旧路径和将来用户态链接器复用的材料，
新进程内核加载路径应绕开动态链接职责，而不是扩大这些能力。
其分阶段资源管理仍值得复用；职责拆分见第 11 篇。

现有 [dynamic_app 模板](../build/templates/dynamic_app.gni) 生成不带 `PT_INTERP`、由内核完成动态链接的 PIE。
因此现成的动态 hello 不能直接作为新启动契约的标准样例。

## 如何确认自己掌握了

对样例运行 `readelf -hW/-lW/-dW/-rW`，回答：

1. 是否有解释器、外部库依赖和运行时重定位？
2. 谁会执行第一条用户指令，谁负责修补地址？
3. 把 bias 从 `0x400000` 改为 `0x600000` 时，段、入口、重定位目标与指针值如何变化？
4. 如果当前内核完全不修改重定位槽，这个样例为何仍能运行？
