# 11. 实现路线与对接

本篇把前面的知识对应到具体工作。最高设计和基线见 [README](README.md)。
以下接口名和里程碑是建议方案，尚未在仓库实现，也不是已经与其他负责人确认的约定。

## 先看两条不同的调用链

基线的单映像入口 [prepare_image](../kernel/loader/src/lib.rs)：

```text
admit → inspect → plan → allocate → map → decode → relocation → cache → seal
```

基线的 [application loader](../kernel/kernel/src/application/loader.rs) 使用更完整的链路：

```text
DynamicLinker::begin → close_dependencies → freeze_scopes → relocate → seal → publish
```

目标中的内核加载链路应是：

```text
校验/规划主 ELF → 映射 PT_LOAD
  → 读取 PT_INTERP，必要时校验/映射解释器
  → 构造用户栈 → 完成段权限与执行前同步
  → 交付首次 PC、SP 和映像资源
```

这里没有内核依赖闭包、符号搜索、重定位和构造函数计划。
现有 `prepare_image` 不能靠传入一个不做事的 relocator 直接变成目标接口。

## 从哪些代码复用

| 位置 | 已有能力 | 本次处理 |
| --- | --- | --- |
| [reader.rs](../kernel/loader/src/reader.rs)、[VFS reader](../kernel/kernel/src/application/adapters/vfs_reader.rs) | 按偏移读取 ELF | 复用，确定读取期间文件稳定性 |
| [image_loader.rs](../kernel/loader/src/image/image_loader.rs) | 头部解码、可信 profile 校验 | 复用；profile 来自平台，不由不可信文件自行决定 |
| [admit.rs](../kernel/loader/src/image/admit.rs)、[inspect.rs](../kernel/loader/src/image/inspect.rs) | Program Header、入口、布局检查 | 复用并拆开动态链接策略；补解释器路径处理 |
| [plan.rs](../kernel/loader/src/image/plan.rs) | 固定/可移动分配请求、bias | 接入用户 VA 与页粒度 |
| [allocate.rs](../kernel/loader/src/image/allocate.rs) | 段复制和 BSS 清零 | 复用，覆盖非平坦后端 |
| [memory.rs](../kernel/loader/src/memory.rs) | 内存接口、lease、事务和提交 | 适配真实地址空间并扩大整体回滚范围 |
| [seal.rs](../kernel/loader/src/image/seal.rs)、[cache.rs](../kernel/loader/src/cache.rs) | 权限计划和架构同步 | 拆出进入用户态前的处理，不提前锁定 RELRO |
| [dynamic_linker](../kernel/loader/src/dynamic_linker/) | 依赖、符号、重定位、生命周期 | 不进入新内核加载路径；是否用于用户态另行评估 |
| [application](../kernel/kernel/src/application/) | VFS 适配、资源管理和启动编排 | 按职责复用，替换平坦内存、线程入口和启动信息协议 |

部分阶段类型是 `pub(crate)`，不是外部可以任意拼装的公共接口。
适合在 loader crate 内新增职责清晰的入口，复用内部阶段，而不是在 application 中复制解析器。

前置 `admit/inspect` 也会按当前 `LoadPolicy` 检查动态特性；
不能只删除最后的 `relocation()`，保留前面的内核链接能力限制不动。
同样，当前 `seal` 包含“已经完成重定位”的假设，需要拆分。

## 建议的接口边界

下列是概念接口，不是现有 API，也不固定由哪个文件实现：

```text
map_elf(reader, trusted_profile, address_space)
  → 映像所有权、load_bias、entry、PHDR 信息、可选解释器路径

prepare_process_image(main_file, argv, envp, address_space)
  → 主程序/解释器/栈资源、initial_pc、initial_sp、main_entry
```

`map_elf` 负责一个映像，外层负责主程序与解释器的编排和共同失败边界。
内存接口应表达用户范围的预留、分配/映射、写入、清零、保护、同步与释放。
对接前可使用模拟后端，不必先给许昌规定一个具体 trait 名称。

返回的数值必须附带有效资源所有权，或由明确的地址空间所有者持续持有资源。
加载器不应自行把入口转换成函数调用来启动进程。

## 按可验收结果推进

### 第一步：独立的映像加载路径

复用校验、布局、复制和清零，实现不执行动态链接的路径。
明确支持的 ELF 类型、目标 profile、页粒度、布局与资源上限。

验收：用模拟后端检查多个 PT_LOAD、非零最低 p_vaddr、BSS、入口、权限请求和失败回滚。
用户基址故意与存储指针不同；用合成输入确认重定位槽没有被内核额外修改。

### 第二步：解释器与用户栈

新增 `PT_INTERP` 路径校验和文件解析接口。将解释器映射到同一地址空间，检查冲突并拒绝解释器递归。
解释器具有启动入口，不能把它当成可忽略 e_entry 的普通依赖库。

构造 `argc/argv/envp/auxv`，所有指针使用用户地址。
分别记录主入口与首次入口，并正确生成 PHDR、ENTRY、BASE 等约定项。

验收：在模拟地址空间反向解码栈，核对最终 SP 对齐、终止项、字符串和地址；
主程序加载成功后，模拟解释器或栈失败，确认整体回滚。

### 第三步：真实地址空间与首次用户态执行

接入许昌的内存接口和 process 的启动接口，准备匹配用户栈 ABI 的最小 `_start`。
建议先跑无外部依赖、无需运行时重定位的 PIE，检查数据、BSS、参数并通过约定陷入报告结果。

验收：记录实际用户特权状态、初始 PC/SP、系统调用来源；另行测试只读页写入或未映射访问。
打印日志、使用 SWI 配置或运行旧 dynamic 测试，不能代替这些证据。

### 第四步：完整动态链路

先用测试解释器验证首次入口、auxv 和转交主程序，再接真正的用户态 `ld.so`。
正式解释器需要能自举，并通过系统调用完成所需的文件访问、内存映射和权限调整等操作。
具体调用集合取决于选定实现，不能默认现有内核已经提供兼容 Linux 的接口。

验收：由用户态加载依赖、修补地址、完成运行时初始化，再进入主程序；
内核日志应仍只体现主映像和解释器装载，不重新承担符号绑定。

这些步骤是建议实施顺序。首个交付是否必须包含第四步，需要由刘闯确认；
阶段性先跑无解释器 PIE 不改变最终必须支持解释器的设计。

## 现在可以独立完成什么

- 拆分加载阶段和策略，保留既有安全检查、所有权与回滚保证。
- 编写用户栈布局器，用参数化字长、对齐和用户地址的方式独立测试。
- 通过内存中的假文件目录测试解释器路径和双映像加载，不等待真实 VFS 布局。
- 自建受控 ELF 测试输入，用 readelf 固定其能力需求；构建匹配栈式入口的最小载荷。
- 整理交付结构和内存操作需求，把待确定的 ABI 参数显式标出。

这些工作不需要等待正式样例 ELF、真实页表完成或完整 ld.so 出现。
ABI 未定项可以参数化并按明确的测试假设推进，不能把测试假设写成已确认的产品约定。

## 对接时问什么

| 对接方 | 需要拿到的结论 |
| --- | --- |
| 刘闯 / process 负责人 | 首期目标平台和验收范围；地址空间创建与所有权；接收的入口/SP/资源形式；用户线程、内核栈和退出由谁完成 |
| 许昌 | 用户地址范围与页粒度；预留/映射/写入/保护/释放接口；内核访问离散页的方式；缓存/TLB 与跨核同步责任 |
| 刘闯协调运行时负责人 | 谁提供栈式 `_start` 和用户态 ld.so；解释器路径、auxv、初始寄存器和系统调用 ABI；正式 ELF 与配套库如何构建 |
| 施涵格 | crate 内阶段的复用/拆分方式，如何保留旧路径回归；动态链接代码将来迁移用户态的可行边界 |

“内核是否做符号解析”和“是否继续使用旧自定义启动结构”已由最高设计回答，不必再作为选项征询。
请求样例时应要源码/构建方法、ELF 和启动约定；动态样例还需解释器与共享库。
只有一个二进制文件不足以形成稳定的联调契约。

## 哪些地方与架构相关

| 内容 | 处理位置 |
| --- | --- |
| ELF class、字节序、machine、flags、入口对齐 | loader 的可信 profile 和校验 |
| 指针宽度、初始栈对齐、初始寄存器、auxv 扩展 | 用户栈构造与运行时/arch 的 ABI 契约 |
| 用户地址范围、页粒度、硬件权限、TLB | 地址空间后端 |
| 写入代码后的指令可见性、跨核同步 | cache / 内存 / arch 接口 |
| AArch64 EL0、RISC-V U-mode 的进入与异常返回 | process / arch，不能照抄 x86 的 CR3/TSS/IRET |
| 重定位编码和执行规则 | 用户态链接器；不放回内核加载路径 |

文件读取、一般范围检查、段拷贝/清零、解释器编排、事务管理大体可共用。
不要因此假定所有架构共用相同页大小或启动寄存器，也不必为每个架构重写整个 loader。

## 首笔改动的建议范围

增加可以独立测试的映像加载入口，并给出匹配的模拟后端测试；
保留现有 application 路径作为回归基线，逐步将新用户进程入口接到新路径。
避免一次把 DSO 全局注册表、dlopen、构造函数管理和整个 application 全部改为进程模型。
它们的旧实现依赖已链接映像与共享平坦地址，不能只改对象名称就宣称符合新设计。

完成第一笔改动后，应能明确回答：内核加载了哪些字节、放在哪个用户地址、保留了哪些资源，
以及下一阶段构造栈和加载解释器还需要什么信息。
