# 10. 验证与联调

验证 loader 最有效的方式是逐层建立证据：文件是什么，加载后内存是什么，CPU 从什么状态开始，
以及异常发生在哪里。只有一条“测试成功”的日志，往往无法说明哪一层已经正确。

本篇的新进程场景是待实现的验收指南；已有旧路径回归记录见第 09 篇。
本次文档编辑没有运行新进程测试，也不把已有 application 测试当作用户态证据。

## 先区分四种成功

| 证据                                     | 能说明什么                   | 尚不能说明什么               |
| ---------------------------------------- | ---------------------------- | ---------------------------- |
| 解析 ELF 成功                            | 输入被解析器接受             | 布局、架构和运行时依赖受支持 |
| 加载后字节正确                           | 复制、清零等内容处理符合预期 | 指令执行、栈和用户权限正确   |
| 函数型载荷返回预期值                     | 当前调用环境中执行了这段代码 | 独立地址空间和用户态启动正确 |
| 用户程序在约定状态运行并通过系统调用交互 | 首个进程链路有了直接证据     | 所有权限与失败路径都完整正确 |

[当前集成测试][ref-1] 的成功执行路径把入口转换成函数指针再调用，属于第三类，不能直接当作第四类。

## 第一步：固定一个可解释的样例

首个样例应只使用当前支持的能力，例如少量代码、已初始化静态数据、零初始化数据，以及一个约定的退出或报告机制。

第一阶段建议选不需要运行时重定位、没有共享库依赖的 PIE，并用 `readelf` 检查，而不是依赖编译参数猜测。
它成功只证明这类受控产物能启动。后续动态联调再增加确实产生重定位的指针和外部函数调用，
验证由用户态运行时完成修补，内核加载器不代劳。

先约定架构、ELF 类型、解释器、重定位责任和入口 ABI。
不要在调试 loader 时同时更换这些条件，否则很难判断哪一次变化解决了问题。

## 第二步：用 readelf 检查真实产物

先按第 09 篇找到被加载的实际 ELF。下面 `ELF` 的赋值是占位示例，需替换为真实绝对路径：

```sh
ELF=/absolute/path/to/actual-loader-test-app
readelf -hW "$ELF"
readelf -lW "$ELF"
readelf -dW "$ELF"
readelf -rW "$ELF"
readelf -sW "$ELF"
```

- 选项：`-hW`
  优先看什么：Class、Data、Machine、Type、Entry

- 选项：`-lW`
  优先看什么：LOAD 的 Offset/VirtAddr/FileSiz/MemSiz/Flags/Align，
  是否有 INTERP/TLS

- 选项：`-dW`
  优先看什么：NEEDED、重定位表等动态信息；没有动态信息也可能是预期结果

- 选项：`-rW`
  优先看什么：实际重定位类型、目标位置和 addend

- 选项：`-sW`
  优先看什么：有符号表时查入口和测试变量位置

`readelf` 检查 ELF 元数据通常不需要宿主与目标架构相同。
反汇编则需要支持目标指令集的工具，例如对应架构的 GNU objdump，或构建时启用了该后端的 LLVM 工具：

```sh
llvm-objdump -d "$ELF"
```

若工具报告不支持架构，先换正确工具，不要立即认定 ELF 损坏。

## 第三步：先验证内存结果

可使用能记录写入的测试后端，或在真实后端上以受控方式检查目标内容。重点选取：

| 场景               | 观察结果                                 |
| ------------------ | ---------------------------------------- |
| 文件段正常复制     | 目标字节与文件对应区间相同               |
| 非零旧内存上的 BSS | `filesz..memsz` 全部为零                 |
| 纯零段、跨页段     | 边界处没有遗漏或多写                     |
| 段间空洞           | 未被错误地当作合法入口，权限和分配符合策略 |
| 不同 load bias     | 段、入口和 PHDR 的用户地址正确变化，文件偏移不变 |
| 两段共享页         | 第二段处理不破坏第一段内容               |

测试内存后端应使用户地址与宿主缓冲区地址不同，验证入口和栈中的指针仍使用用户地址。
页内可见填充也应检查，不只检查 BSS。

新增测试至少覆盖：

| 场景 | 观察结果 |
| --- | --- |
| 主程序带 `PT_INTERP` | 解释器被加载到同一地址空间，首次 PC 指向解释器 |
| 主程序与解释器 bias 不同 | `AT_ENTRY` 指向主程序，`AT_BASE` 按 ABI 描述解释器 |
| PHDR 在文件中的偏移不等于虚拟地址 | `AT_PHDR` 通过映射关系计算，不能盲用 `B + e_phoff` |
| 空 envp、多参数、不同长度字符串 | 终止指针、目标字长、字节序和最终 SP 对齐正确 |
| 栈空间不足、解释器缺失 | 返回对应错误，已分配资源全部回收 |
| 主程序加载成功后解释器或栈失败 | 不留下已发布的半个进程 |
| 存在待用户态处理的重定位槽 | 内核只执行拷贝/清零，不擅自修补槽内容 |
| RELRO 覆盖可写数据 | 进入解释器前未被提前锁死；完整联调时验证用户态后续收紧权限 |

为检查内核未执行重定位，可以使用合成 ELF 和测试内存，只检查映射结果而不执行它。
未知重定位的拒绝测试属于用户态链接器的语义测试，不能继续作为内核映像加载器的通用拒绝条件。

这些可以大多在纯 Rust 或测试内存模型里验证，不必每个错误都等到 CPU 崩溃后才发现。

## 第四步：在 QEMU 中观察执行

QEMU 模拟目标机器，让你可以在宿主上运行 AArch64/RISC-V 的系统软件。
它不是把目标机器码变成普通宿主函数调用。

semihosting 是另一回事：目标程序通过模拟器/调试环境获得宿主文件访问、输出等服务。
[当前 loader 测试][ref-1] 使用 semihosting 读取宿主中的 ELF 文件。
这能简化测试，但不能据此证明内核 VFS 或用户系统调用已经完成。

优先使用 [测试构建配置][ref-2] 生成的 QEMU runner，避免手工拼接 CPU、机器型号、内存、
设备和加载地址时引入新的变量。

建议记录一组紧凑但有意义的加载日志：架构、ELF 类型、bias、各段文件区间与用户区间、最终权限、主入口、首次入口、
初始 SP，以及失败阶段。

日志字段直接标明 `user_va`、`file_offset` 等坐标，
比打印一个没有说明的 `addr` 更利于定位问题。

## 第五步：需要时使用 GDB

QEMU 常见的 `-S` 表示启动后先暂停 CPU，`-s` 通常启用 1234 端口的 GDB 服务。
实际应查看仓库生成的调试 runner，避免重复参数和端口冲突。

典型 GDB 操作如下，其中文件路径和地址必须替换为真实值：

```text
file /absolute/path/to/kernel-or-test.elf
target remote :1234
break /absolute/path/to/loader/source.rs:LINE
continue
info registers
```

上面的文件行号是占位符，应换成新加载入口的实际位置；原有 `load_elf` 不一定经过新路径。
Rust 符号名称和优化也可能影响按函数名断点，可使用验证过的实际地址。
程序载荷被 loader 放入内存后，还需要为它加载与运行时地址对应的符号。

GNU GDB 支持的 `add-symbol-file ... -o OFFSET` 可用于整体偏移一致的映像；
其他情况需按段地址配置。传入的是正确的符号偏移关系，不能无条件把最低映射地址当成 bias。

```text
add-symbol-file /absolute/path/to/payload.elf -o 0x400000
```

上面的数值只适用于前文教学例子的 bias，不是本仓库默认值。
符号地址正确后，在运行时入口断住，检查 PC、SP、指令字节和栈内容，通常比盲目追踪所有启动汇编更直接。

## 异常日志最少要保留什么

通用信息包括：执行位置 PC、访问的故障地址、异常原因、当前特权状态、相关进程或地址空间标识。

- 架构与执行环境：AArch64，异常进入 EL1
  常见诊断寄存器：`ELR_EL1`、`ESR_EL1`、适用时的 `FAR_EL1`，并结合保存的状态

- 架构与执行环境：RISC-V，陷入 S-mode
  常见诊断寄存器：`sepc`、`scause`、适用时的 `stval`

- 架构与执行环境：RISC-V，陷入 M-mode
  常见诊断寄存器：`mepc`、`mcause`、适用时的 `mtval`

不是每类异常都会提供有效故障地址，应结合异常种类解释字段。
[当前 RV trap 实现][ref-3] 使用 M-mode 相关寄存器，不要直接套用 S-mode 日志说明。

可以按现象缩小范围，但不要只凭现象定案：

- 入口第一条取指失败：优先核对入口坐标、映射、执行权限和当前特权状态。
- 读全局变量时失败：核对数据段、重定位、BSS 和访问权限。
- 刚进启动代码就访问奇怪地址：核对 SP、参数布局和 ABI。
- 跳到 ld.so 后失败：核对解释器映射、auxv 及它实际需要的系统调用。
- 重复加载或更换 bias 后才失败：核对清零、资源生命周期、旧映射与地址假设。

## 第六步：证明进入了用户态

与 process 模块联调时，验收不能只看“打印了某个字符串”。应组合可观察证据：

1. 在目标用户特权级从约定入口执行，初始 SP 和地址空间正确。
2. 用户程序检查 `.data/.bss` 和入口参数；动态阶段再验证用户态完成的重定位。
3. 通过约定的陷入/系统调用进入内核，并能从日志确认陷入来源；直接调用内核函数不算同一件事。
4. 单独的负面样例访问未映射区或写只读页，产生预期故障，由内核按约定处理。
5. 正常退出与装载失败后，映像资源得到回收。

权限负面样例需要独立运行，避免一个预期故障阻止后续测试。两个进程映射同一用户地址但读到各自内容，
则可以进一步验证地址空间隔离。

## 区分旧测试、新加载测试和完整动态联调

`98a6f0cf` 的 loader 集成测试使用 `loader_test_exec` 等配置条件选择载荷和断言。
[no_std 载荷][ref-4] 也有自身的测试入口协议；旧文档有关 ARM/AArch64 主断言排除的描述已过时。
评估覆盖范围要看实际构建配置和当前源码。

application 现有 dynamic 测试覆盖内核完成动态链接的路径。
当前 [AArch64 Context::init](../kernel/kernel/src/arch/aarch64/mod.rs) 设置 `spsr = 0b0101`（EL1h），
配合 application 创建普通线程的流程，不能据此声称已经在 EL0 执行。

此外，[测试分组](../kernel/tests/BUILD.gn) 暂时排除了 dynamic stack reclaim suite，
[dlopen 测试](../kernel/tests/dynamic_dlopen_test/src/test.rs) 暂时注释了堆用量相等断言。
已有动态测试通过不代表资源回收已被完整验证。

建议按四级验收：

1. 模拟地址空间验证加载内容、解释器选择、用户栈与整体回滚。
2. 无解释器最小 PIE 在真实用户态运行，通过约定陷入报告结果。
3. 测试解释器检查 auxv、确认首次进入自己，再转交主程序。
4. 正式 `ld.so` 自举、加载 libc 等依赖、完成重定位和运行时交接，最后进入程序。

第 3 级可以完全没有真实动态链接能力，不能把它称为完成了 `ld.so`。
第 4 级需要运行时实际使用的文件、映射、保护等系统调用，不能只靠 loader 一方实现。

一份可复现记录应包含：代码版本、工具链、GN 参数、主程序/解释器/依赖库标识、
ELF 关键信息、执行命令、观察到的特权状态、实际断言及未验证部分。
