# 08. 校验与失败恢复

loader 应将输入看成可能损坏、不受支持或具有异常资源需求的文件。
这里的目标很具体：
无效程序应返回可解释的错误，不越界写内存，不让已存在的进程处于半替换状态，
也不泄漏加载过程中分配的资源。

你熟悉的 `Result`、`checked_add`、所有权和分阶段提交，在这里都可以直接发挥作用。

## 把检查分成四层

| 层次       | 要检查什么                                               |
| ---------- | -------------------------------------------------------- |
| 格式       | magic、类别、字节序、表的位置/大小/数量、文件是否截断    |
| 执行语义   | 架构和启动 ABI、支持的类型、段大小、入口、解释器需求 |
| 布局与策略 | 用户地址范围、页对齐、权限冲突、栈/解释器冲突、资源上限  |
| 运行时操作 | 分配、读取、映射、写入、保护设置是否成功                 |

解析库主要帮助第一层，也可能完成部分后续检查，但不能假设它理解你的内核布局和支持范围。

## 边界检查先防算术溢出

下面这种写法不够：

```rust
// 问题示例：加法可能在比较之前溢出。
if offset + length <= buffer.len() {
    // ...
}
```

debug 模式可能 panic，release 行为又可能不同。对 ELF 外部字段，先有检查地转换，再有检查地相加：

```rust
fn file_range(
    offset: u64,
    length: u64,
    file_len: usize,
) -> Result<core::ops::Range<usize>, &'static str> {
    let start = usize::try_from(offset)
        .map_err(|_| "offset too large")?;
    let len = usize::try_from(length)
        .map_err(|_| "length too large")?;
    let end = start.checked_add(len)
        .ok_or("file range overflow")?;
    if end > file_len {
        return Err("file range outside input");
    }
    Ok(start..end)
}
```

这是独立的教学辅助函数，只验证文件切片范围，不构成完整 ELF 校验器。

同样的原则适用于：`phnum * phentsize`、`vaddr + memsz`、`B + e_entry`、
向上对齐，以及参数字符串总长度。
64 位字段转换到较窄的 `usize` 时，`as` 截断尤其容易隐藏错误。

## 每个 `PT_LOAD` 至少明确哪些条件

- `p_filesz <= p_memsz`，文件内容区间有效。
- 虚拟区间、加上 bias 后的用户区间均没有溢出。
- 区间位于内存模块允许的用户地址范围，不覆盖内核保留区域。
- `p_align` 和目标平台的页对齐条件符合支持策略。
- 请求的权限组合受支持，页级权限冲突有明确处理方式。
- 空段、纯零段、字节重叠和页共享都有定义好的行为。

主程序、解释器和栈还需要做全局冲突检查。
只验证每一项“自身看起来合法”，无法证明组合后的布局合法。

## 入口不是落在总包围范围里就够了

两个可加载段之间可能存在未映射空洞。
即使入口在“所有段最小起点到最大终点”的大区间内，也可能落在空洞中。

通常应验证首次执行入口属于实际映射的、允许用户执行的段，
并满足目标指令集的入口对齐和支持策略。
目标指令对齐不能统一假设为 4 字节，
例如 RISC-V 是否支持压缩指令会影响要求。

解释器入口和主程序入口都要验证，但它们在启动协议中承担不同角色。

## 检查解释器，同时守住动态链接职责边界

对 `PT_INTERP` 检查文件区间、数量、路径长度和 NUL 终止符；
检查解释器自身的类型、架构、段布局和可执行入口。
应拒绝解释器再次要求另一个解释器，避免递归加载。
具体路径命名与查找规则由 VFS 和运行时契约确定，不能硬编码成某个 Linux 发行版的路径。

解释器不是由内核解析 `DT_NEEDED` 找到的库，加载解释器也不意味着在内核修补它的 GOT。
解释器必须有能够接管初始状态的启动实现；需要自重定位时，由它的用户态早期代码完成。

当前代码按内核动态链接器能力拒绝部分动态标记、重定位与 TLS 特性。
新路径要保留映射所需的结构和范围校验，但不应因内核不会执行某种重定位就拒绝可由用户态处理的 ELF。
重定位类型、符号、写入目标的语义校验由真正执行重定位的用户态链接器承担。

`PT_TLS` 描述模板，通常其初始化内容由可加载段承载；为线程建立 TLS 实例和设置线程指针是运行时/线程模块工作。
首期是否支持原生 TLS 仍需约定，不能把旧分支使用 emutls 与支持原生 `PT_TLS` 混为一谈。

## 资源上限也是必要的正确性条件

一个很小的 ELF 可以声明很大的 `p_memsz`，或者把两个小段放在极远的位置。
若按“最大地址减最小地址”分配连续存储，可能产生远超文件大小的分配请求。

因此应按项目目标限制映像总大小、页面数、段数、参数长度和解释器数量等。
稀疏虚拟地址布局不应自动迫使你为中间所有空洞分配物理内存。

内存不足是正常错误路径，不应该成为 panic 或留下部分映射的理由。

## 将装载看成一次事务

推荐的逻辑阶段是：

```text
读取并验证元数据
    ↓
形成加载计划，检查全局布局和功能支持
    ↓
在尚未发布的新地址空间中加载主程序和解释器、复制、清零、建栈
    ↓
完成进入用户态前的段权限与架构同步（不提前锁定待重定位的 RELRO）
    ↓
成功提交，将映像所有权交给进程
```

失败发生在提交前，应撤销新映像的资源，保留旧进程可用状态。
文件读取和映射仍可能在规划完成后失败，
因此“先校验”不能代替回收机制。

如果输入会在装载期间变化，还要约定使用稳定快照、持有文件对象或其他一致性策略。
不能验证一份字节，随后却装载另一份内容。

## 回收顺序为什么重要

如果物理页仍被有效页表引用就先释放，
分配器可能把它交给其他用途，旧映射仍能访问这块已经复用的内存。

通常需要先确保映像不再被执行或访问，
撤销映射并完成内存模块要求的同步，再释放相应资源。
未发布的新地址空间更容易做到这一点。

固定用户虚拟地址不等于借用或覆盖内核中的同地址存储。
`ET_EXEC` 也应在新地址空间中建立自己的映射。旧后端若直接覆盖借用的活跃内存，
失败后单靠析构不能恢复旧字节；这种限制不能成为新进程加载时覆盖旧映像的理由。

## 对照 `98a6f0cf`

[现有集成测试][ref-1] 和 [crate 内测试](../kernel/loader/src/tests/) 可作为复用基础。
[prepare_image][ref-2] 配合 [memory.rs][ref-3] 已建立分阶段加载、lease 和失败回滚机制。
本次的新增重点是：在不执行内核动态链接的路径中保留这些保证，并扩大到主程序、解释器、用户栈的整体事务。

旧 `BorrowedFixed` 模式可能对写坏的借用区间标记 poisoned；这不能替代新进程的独立映射与回收。
未来实现 `execve` 时还需要保证准备失败不破坏旧地址空间；首个进程阶段先保证失败不发布半成品。

## 如何验证失败路径

测试应至少选取具有不同失效机制的输入：
截断表、整数溢出、`filesz > memsz`、入口落空洞、解释器路径缺少终止符、
解释器打开失败、栈空间不足、分配或权限设置中途失败。

观察的不只是 `is_err()`，还包括失败前后资源计数一致、旧映像未被替换、无关目标字节未变。
可以让测试内存后端在第 N 次分配或映射时失败，从而稳定覆盖难以自然复现的错误路径。

能说明“第三页映射失败后，前两页和页表页由谁回收”，才算真正理解失败恢复。
