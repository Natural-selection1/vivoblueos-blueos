# 09. 交叉编译与链接

loader 能支持什么程序，一半取决于 loader，另一半取决于工具链到底产出了什么 ELF。
目标是让你能追踪“Rust 源码 → 编译参数 → 链接参数 → ELF 属性”，而不必先学会重写整个构建系统。

实现基线为 `98a6f0cf`，本地环境参考 `2740fe19`。何归已完成新工具链的 rustup link/override，
并在 `.envrc` 中停用旧 Rust 路径导入。下面区分旧路径回归命令与尚需新增的用户进程产物。

## host 和 target

host 是编译工具运行的平台，target 是生成程序要运行的平台。
你可以在 x86_64 Linux 上执行 `rustc`，生成 AArch64 或 RISC-V 机器码。

target 不只表示指令集，还涉及字长、ABI、操作系统环境及编译器约定。
某个 ELF 的 `e_machine` 是 AArch64，不意味着它就能运行在任意 AArch64 系统上；
它可能依赖 Linux 系统调用、动态链接器和 TLS 机制。

工具链还包括链接器、目标库、汇编/反汇编工具等。`rustc --version` 相同，
不足以证明两个环境生成相同产物。

## 从 Cargo 迁移到 GN/Ninja 的认识

| 你在 Cargo 中熟悉的职责               | 本仓库中主要看哪里                          |
| ------------------------------------- | ------------------------------------------- |
| crate 依赖与构建目标                  | `BUILD.gn` 中的 target、`deps` 和模板       |
| features / 编译条件                   | GN 参数、生成配置、传给 rustc 的 `--cfg` 等 |
| `.cargo/config.toml` 的目标与链接设置 | board 配置和 toolchain 定义                 |
| `build.rs` 的生成工作                 | GN `action`、生成脚本和模板                 |
| `cargo build/test` 的执行             | 先 GN 生成构建图，再 Ninja 执行目标         |

这不是一一对应的语法替换。GN 是构建描述与生成工具，Ninja 根据生成的依赖图决定哪些编译、链接、
脚本和测试命令需要执行。

Rust 最终仍由 rustc 编译。只是 crate 依赖、参数、输出位置等由 GN 模板组织，
不能假设修改 `Cargo.toml` 或运行 `cargo test` 就会影响当前构建路径。

## target label 是什么

GN 的 `//kernel/loader:blueos_loader` 表示仓库根下该目录中的命名构建目标。
这里的 `//` 是 GN 的仓库根标记，不是操作系统文件路径。

[loader 的 BUILD.gn][ref-1] 中：

- `blueos_loader` 是 Rust 库目标。
- `check_loader` 包含集成测试，在配置了 QEMU 时还包含 crate 单元测试。
- `inputs` 是生成测试输入的分组目标。

`group` 本身通常不编译一段源码；构建它会沿依赖关系触发其他目标。
阅读构建文件时，要追到真正的编译目标和执行测试的 action。

## 编译阶段与链接阶段各决定什么

rustc 将 Rust 编译成目标代码；最终链接把目标代码和库组合起来，解析符号，安排布局，生成 ELF。

链接器还可能决定 ELF 类型、入口、Program Header、是否保留动态重定位，以及是否写入解释器路径。

链接脚本可以控制地址布局。例如 [固定地址测试脚本][ref-2] 包含：

- `ENTRY(_start)`：选择入口符号。
- `MEMORY`：声明测试可用区域。
- `PHDRS`：声明 `PT_LOAD` 与段权限。
- `SECTIONS`：安排 `.text/.data/.bss`。

链接脚本描述的是本次产物的布局；不要把内核镜像的链接脚本直接拿来当通用用户程序脚本。

## `no_std`、`no_main` 和几个链接参数

`#![no_std]` 表示不默认使用 Rust 标准库，不表示代码天然可独立启动。
仍可能需要分配器、panic handler、编译器运行时辅助函数，以及项目自己的系统调用包装。

`#![no_main]` 表示不采用通常的 Rust main 入口安排。程序需要自行提供与构建配置匹配的启动入口。

- 参数或概念：`-C relocation-model=pic`
  作用：请求生成位置无关代码
  常见误解：不能单独保证最终是可运行 PIE

- 参数或概念：链接器的 `-pie`
  作用：请求链接为 PIE
  常见误解：还要看工具链支持和其他参数组合

- 参数或概念：`-static`
  作用：请求静态链接相关选择
  常见误解：不等于没有运行时重定位

- 参数或概念：`-static-pie`
  作用：支持它的工具链中用于静态 PIE
  常见误解：并非所有裸机链接环境都实现同样语义

- 参数或概念：`-nostartfiles`
  作用：不自动加入通常的启动文件
  常见误解：需要自己承担原来由启动文件完成的工作

- 参数或概念：`-no-dynamic-linker`
  作用：不设置动态解释器
  常见误解：不会自动替你生成自重定位启动代码

`-Clink-arg=...` 是 rustc 向链接命令传参数的一种方式；
当链接命令是 GCC 驱动时，`-Wl,...` 又表示继续把参数传给底层链接器。
要先确认当前调用的是驱动还是裸链接器，再解释参数含义。

依赖库也重要：主 crate 用 PIC 编译，但链接进来的其他对象采用不兼容的绝对地址假设，仍可能破坏可重定位性。

文件后缀也不是可靠标准。`.so` 通常表示共享对象，但把文件改名不会改变 ELF 类型、入口或运行时需求。

## 先确认实际调用的是新 rustc

rustup 的目录 override 只对经过 rustup 代理启动的编译器生效。
本仓库构建会调用 `PATH` 中的 `rustc`；旧 shell 仍可能保留 `/opt/sysroot/usr/local/bin`，
所以修改 `.envrc` 后不能只看 `rustup show` 就认定实际编译器已切换。

```sh
command -v rustc
rustup show active-toolchain
rustup which rustc
rustc -vV
rustc --print sysroot
```

本地已链接的名称是 `rust-loader-dev`。必要时对构建命令显式前置 rustup 代理目录：

```sh
env PATH="$HOME/.cargo/bin:$PATH" rustc -vV
```

[工具链 PR #14](https://github.com/vivoblueos/rust/pull/14/files) 调整 PIC 和动态链接能力。
它让编译器能够生成所需产物，不会提供用户态页表、栈式 `_start` 或可运行的 `ld.so`。
应用及其依赖需要相容的 PIC/链接配置；内核自身不必因此统一改成 PIC。

## 复现旧路径回归基线

以下从仓库根开始，用 AArch64、debug、`direct_syscall_handler=false`：

```sh
env PATH="$HOME/.cargo/bin:$PATH" gn gen out/loader-review-a64.debug.swi \
  --args='board="qemu_virt64_aarch64" build_type="debug" direct_syscall_handler=false'
env PATH="$HOME/.cargo/bin:$PATH" ninja -C out/loader-review-a64.debug.swi \
  kernel/loader:check_loader kernel/tests/dynamic_test:run_dynamic_test
```

此前基线检查在这套配置下通过了 40 个 loader 单元测试、4 个 loader 集成测试和 1 个 dynamic 测试。
这是旧加载/application 路径的回归证据，不是用户进程或新设计的验收结果；本次文档编辑没有重新运行它们。
`direct_syscall_handler=false` 也不能单独证明应用已在用户态运行。

当前集成测试根据 `loader_test_relocation` 生成 `loader_test_exec` 条件，
选择固定地址载荷及相关断言。不要继续用旧文档的“只在 release 编入执行测试”判断覆盖范围。
应直接查看当前 [测试 BUILD.gn](../kernel/loader/tests/integration_test/BUILD.gn) 和用例条件。

可以查询实际依赖、编译命令和输出：

```sh
gn desc out/loader-review-a64.debug.swi //kernel/loader:check_loader deps --tree
ninja -C out/loader-review-a64.debug.swi -t commands kernel/loader:check_loader
gn desc out/loader-review-a64.debug.swi \
  //kernel/loader/tests/integration_test:loader_integration_test outputs
```

最后一个目标是测试执行程序。真正被加载的输入应沿依赖树找到
`exec_app:loader_test_app` 或 `no_std_app:loader_test_app`，再查询其输出。

## 为目标设计新增产物，不能只沿用 dynamic_app

[dynamic_app.gni](../build/templates/dynamic_app.gni) 明确使用 `--no-dynamic-linker`，
并通过 `blueos_scrt1` 接收旧的启动信息结构。该模板的目标是内核完成动态链接的 application。

新用户进程至少需要区分下面几种产物；具体 GN target 名称尚未确定：

| 产物                   | 关键条件                                                 | 用途                     |
| ---------------------- | -------------------------------------------------------- | ------------------------ |
| 最小无解释器 PIE       | `ET_DYN`，无外部库依赖，无需运行时重定位；入口读取用户栈 | 首次用户态启动           |
| 测试解释器及配套主 ELF | 主 ELF 带 `PT_INTERP`；解释器可独立从用户栈启动          | 验证双映像加载与入口选择 |
| 正式动态程序           | 正确的解释器路径、共享库、启动代码和系统调用 ABI         | 完整动态联调             |

动态产物需要将解释器路径写入 `PT_INTERP`，但简单删除 `--no-dynamic-linker` 不够：
链接器的默认路径可能不适合 BlueOS，现有 `_start` 也仍是旧协议。
必须一起确定解释器文件、根文件系统位置、crt 和运行时 ABI。

无需等待正式 ELF 才开始写加载器。可以先自建受控样例；向刘闯对接正式产物时，
应索取构建方法和启动协议，有解释器时还需配套解释器与依赖库。

## 用产物验证参数，而不是反过来猜

对实际载荷运行 `readelf -hW/-lW/-dW/-rW`，检查架构、类型、入口、段、解释器、动态依赖和重定位。
具体命令见第 10 篇。

[当前 no_std 测试源码][ref-11] 有自身的入口调用约定，不能代替栈式用户启动样例。
此前构建出的 `out/loader-review-a64.debug.swi/bin/hello` 是 AArch64 PIE，
依赖 `libc.so.1` 且没有 `PT_INTERP`。它可以用于观察旧机制，但按新设计需要更换构建/启动方式。

掌握标准是：能找到实际 rustc 和链接命令，解释其中影响 loader 的参数，并用 ELF 输出确认结果。
你不需要先成为 GN 专家。
