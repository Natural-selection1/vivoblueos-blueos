# 06. 程序启动 ABI

Application Binary Interface，应用二进制接口
ABI描述已经编译好的程序之间如何交互，包括寄存器、栈、数据布局和入口状态。
源码层面的函数签名只是其中一部分。

loader 把字节放对位置后，仍须让程序从它预期的初始状态开始。
否则第一条指令可能执行成功，启动代码却马上读取错误的参数或跳到错误地址。

## `_start` 与 `main` 分别处在哪一层

`main` 是语言运行时约定的程序主体。
普通系统程序在进入 `main` 前，通常已经完成部分运行时初始化。

`_start` 是常见的入口符号名称。链接器把所选入口地址写入 `e_entry`；
loader 以 `e_entry` 为准，并不要求文件中一定保留 `_start` 这个符号。

```text
内核准备入口状态
    ↓
可选：动态链接器
    ↓
程序入口 / 启动代码
    ↓
运行时初始化
    ↓
main
    ↓
退出系统调用或约定的终止机制
```

构造函数、TLS 初始化等工作的具体分工取决于 libc、动态链接器和启动运行时。
不能假设所有初始化都由 ld.so 单独完成。

## 进程入口不是普通 Rust 函数调用

普通函数调用由调用者提供合法栈、返回地址和 ABI 规定的参数。
进程入口可能没有普通意义上的返回地址，参数可能位于初始栈上，
返回时也不能随意 `ret` 回内核。

因此，将整数入口强转为 `fn()` 或 `extern "C" fn()` 并调用，
只验证一种约定好的“函数型载荷”。
它不自动建立新进程，也不自动降低特权级。

`extern "C"` 选择的是目标平台的 C 函数调用约定，
不会让函数自动获得 Linux 进程启动语义。

## 初始用户栈放什么

本次最高设计明确要求构造 `argc/argv/envp/auxv` 用户栈。常见布局如下；
完整的字段集合和初始寄存器约定仍须与目标启动代码、解释器对齐。
该示意从初始 SP 向更高地址读取，实际布局还需遵守目标 psABI 和所选运行时：

```text
初始 SP → argc
           argv[0]       ──→ 用户地址空间中的参数字符串
           argv[1]       ──→ 用户地址空间中的参数字符串
           ...
           NULL
           envp[0]       ──→ 用户地址空间中的环境字符串
           ...
           NULL
           auxv 类型、值
           auxv 类型、值
           ...
           AT_NULL, 0
           对齐填充、字符串、辅助数据等（具体排布由构造器决定）
```

`argc` 是参数数量，`argv` 是参数指针序列，`envp` 是环境字符串指针序列。
字符串通常以 NUL 字节结束。

这里的每一个指针都必须是进程可访问的用户地址。
把宿主 `String` 的 `as_ptr()` 写进去，
即使类型和位数恰好匹配，也没有完成跨地址空间的数据搬运。

空环境也需要正确的终止指针。
不要把“没有环境变量”解释为把后面的所有字段省略。

## auxv 是传给运行时的辅助信息

auxiliary vector（辅助向量）是一组整数键值对，
让运行时取得内核已知、但无法只靠参数字符串表达的信息。

| 常见项      | 含义                                       |
| ----------- | ------------------------------------------ |
| `AT_PHDR`   | 主程序 Program Header 表的用户运行时地址   |
| `AT_PHENT`  | 单个 Program Header 的大小                 |
| `AT_PHNUM`  | Program Header 数量                        |
| `AT_PAGESZ` | 页大小                                     |
| `AT_ENTRY`  | 主程序的运行时入口                         |
| `AT_BASE`   | 解释器的装载基址信息，按所选 ABI 填写      |
| `AT_RANDOM` | Linux ABI 中指向 16 字节随机数据的用户指针 |
| `AT_NULL`   | 向量结束标记                               |

这不是所有系统必须完整提供的清单。
本次可以约定首期所需的 auxv 子集，但应保持已确定的栈式启动方向；
选用现成 libc 或 ld.so 时则必须满足它的真实要求，
不能随意漏项或伪造内容。

`AT_PHDR` 尤其容易写错：
`e_phoff` 是文件偏移，不能无条件计算 `B + e_phoff`。

若表位于某个已装载段中，可以根据该段计算：

```text
AT_PHDR = B + 段的 p_vaddr + (e_phoff - 段的 p_offset)
```

前提是整个表都落在该段实际装载的文件内容范围内。
也可以验证并利用 `PT_PHDR`。
若表未装入内存，则需要按照支持策略额外安排有效存储或拒绝该布局。

## 怎样构造栈，才能不混淆地址

一种可实现的方法是：

1. 确定用户栈地址范围和容量，限制参数与环境数据总大小。
2. 从高地址向低地址放字符串和辅助数据，记录它们的用户地址。
3. 按目标字长、字节序生成指针和 auxv 数组。
4. 计算包含整个表后的最终 SP，满足目标对齐，并把必要填充安排在不破坏解析的位置。
5. 将完成的字节布局写到新进程栈中，返回用户 SP。

常见 AArch64 和标准 RV64 ABI 通常涉及 16 字节栈对齐，但应以所选进程启动 ABI 为准。
不能先对齐栈顶，再压入任意数量的字，便认为最终 SP 仍然对齐；
也不能在要求 SP 指向 argc 的 ABI 中让填充占据该位置。

## 有解释器时，有两个入口需要记录

主程序入口仍是 `B_main + e_entry_main`。
如果存在 `PT_INTERP`，
CPU 最先进入的通常是解释器入口 `B_interp + e_entry_interp`。

`AT_ENTRY` 仍应描述主程序入口，供解释器后续交接。
把它改成解释器入口会混淆两个不同角色。

主程序、解释器和栈需要在同一个新进程地址空间中合理放置，互不冲突。

## 谁负责真正进入用户态

loader 一般提供准备好的映像和启动信息；
process/架构模块设置初始寄存器、地址空间和异常返回状态，再进入用户态。

AArch64 常见模型是从内核 EL1 返回到 EL0；RISC-V 的用户态是 U-mode，
通用分页内核常运行在 S-mode。具体启动状态和返回路径取决于平台。
本仓库现有 RV 代码包含 M-mode 路径，
不能直接把它当成已经具备 S-mode 用户进程切换。

CR3、TSS、IRET 属于 x86，不能直接照搬到这两个平台。

## 对照 `98a6f0cf`：启动协议需要替换

[application 协议](../kernel/header/src/application.rs) 明确说明它不是初始进程栈。
`ApplicationStartStorage` 在内核堆中保存 argv、envp、auxv 和构造/析构计划，
[service.rs](../kernel/kernel/src/application/service.rs) 把 `start_info` 作为普通线程入口参数传入。
[AArch64 blueos_scrt1](../librs/start/aarch64/blueos_scrt1.S) 也依赖这个参数协议。

因此，把该结构体连同所有指针搬到用户内存，仍不符合本次规定的栈式启动。
应新增用户栈构造逻辑，并提供从初始 SP 读取参数的配套 `_start`。
现有构造/析构计划不能继续由内核符号解析产生；相关初始化转到用户运行时执行。

[集成测试][ref-1] 的函数型入口和[固定地址载荷][ref-2] 的返回值约定，
也只能作为原有测试协议保留，不能用来定义新进程 ABI。

与 process 对接时，loader 应交付首次 PC、用户 SP、主程序入口及资源所有权。
创建用户线程、准备内核栈、设置异常返回状态由 process/arch 完成。
首个进程可以走创建流程，不要求你先实现完整 `execve` 替换旧进程的语义。

验收前应明确：谁提供 `_start`、哪些 auxv 是必需的、初始寄存器是什么、如何报告结果或退出。
这些是最高设计尚未展开的接口细节，不是重新选择是否使用用户栈。
